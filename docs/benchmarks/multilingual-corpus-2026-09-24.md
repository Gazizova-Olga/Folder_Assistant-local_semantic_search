# Semantic search in three languages, through the search tool

_Measured 2026-09-24 on this machine: Microsoft Windows 10.0.26200, X64, 8 logical processors, Ollama
CPU-only (`ollama ps` reports 100% CPU, no GPU present). Profile `ollama-vec`,
`qwen3-embedding:0.6b`, 1024 dimensions. Regenerate with:_

```bash
node tools/make-corpus.js <folder>
CORPUS_PROBE=<folder> CORPUS_PROBE_DB=<index folder> \
  dotnet test --filter "FullyQualifiedName~MultilingualCorpusProbe" -l "console;verbosity=detailed"
```

**What this measures that `semantic-search-results.md` does not:** the queries go through
`SearchTools.SearchIndex` — the tool the agent calls — so the over-fetch, the passage rebuild and its
chunk-hash verification, the low-confidence screen, the score-gap cutoff and the budget reduction are
all inside the number. The curated benchmark measures the ranking underneath them.

## The corpus

146 files generated by `tools/make-corpus.js`: 12 topics written in **English, Russian and Turkish**,
across **all 31 extensions** the text extraction registry claims, in five directories plus nesting.
File sizes are computed from the real chunk rule (a 256-token window stepping 224), so **66 files end
exactly on a chunk boundary and 64 leave a short trailing chunk**. 130 labelled documents, 144,420
tokens. Beside them sit deliberate edge cases carrying no subject matter: empty, whitespace-only,
one-token, exactly one chunk, one token over a chunk, CRLF, a UTF-8 BOM, both together, a file over
the 1 MB bound, three extensions the registry does not claim, and files under `node_modules`, `.git`,
`bin` and `obj`.

48 labelled queries: one per topic per language, worded to avoid the document's own distinctive
words, plus one cross-lingual question per topic whose answer sits in all three languages. A query is
answered when a file **about that topic** comes back — every copy of the topic in that language is
relevant, not one nominated file.

## Retrieval

| Question asked in | Recall@1 | Recall@3 | MRR | queries |
|---|---:|---:|---:|---:|
| Russian | 100 % | 100 % | 1.000 | 12 |
| Turkish | 92 % | 92 % | 0.917 | 12 |
| English | 73 % | 91 % | 0.818 | 11 |
| cross-lingual | 92 % | 100 % | 0.962 | 13 |
| **all** | **90 %** | **96 %** | **0.927** | **48** |

Five passages asked for per query, which is the tool's default and what the cutoff and the budget
therefore see. Every query came back with five: on this corpus the score-gap cutoff never fired, and
neither did the low-confidence screen (off by default).

**Query latency: p50 151 ms, p95 215 ms** — almost all of it embedding the question.

**The five misses are worth reading.** Three are same-topic documents in another language ranking
first, which the per-language labels count as wrong — "how do I pay when I get there" put the Russian
copy of the mountain-hut rules first and the English copy second. One is a genuine ambiguity: "the
dark layer on top of my culture, is it ruined" retrieved the paper-archive document over the
sourdough one. One is a short, contentless edge file ranking second for a Turkish question, which is
the short-document effect worth watching on a real folder.

## Indexing, and what the shape check verified

| | |
|---|---|
| Files indexed | 136 |
| Chunks | 682 (672 designed + 10 from the six edge files that carry content) |
| Cold index | 2,721 s — **about 4.0 s per chunk**, CPU-only |
| Re-index after changing five files | **14 s, 9 vectors re-embedded** |

The chunk count matching the design to the file is what makes the rest of this table evidence rather
than assertion. It confirms, end to end: the metadata folder, `node_modules`, `.git`, `bin` and `obj`
were skipped; the file over 1 MB was skipped; `.pdf`, `.docx` and `.bin` were not read as text; the
empty and whitespace-only files produced no chunks; and the CRLF and BOM files chunked identically to
their plain twins — a BOM read as content would have changed their hashes and their chunk count.

The re-index line is the unchanged-file rule working: content hash matched and the active model
already held vectors, so only the five rewritten files were embedded again.

## What this cost, and why the deadline moved

A chunk costs what its **model tokens** cost, not a flat amount. On full 256-token windows, measured
here before this run: **2.1 s** for an English chunk, **4.3 s** for a Russian one, 3.0 s per chunk
over a mixed batch of sixteen. A window of 64 mixed chunks is therefore about 190 s of work, and the
shipped 120 s deadline ended every one of them — the first attempt at this corpus failed with
`TimeoutException` on the first batch, retried, and failed again. **`Indexing:OllamaTimeoutSeconds`
moved to 600 s on this tree** (`SPEC-162` 0.11.0); this run completed without a single timeout.

The 600 ms per chunk in `2026-09-16-two-platforms.md` is not contradicted: that corpus is 20 short
English documents whose chunks are far below a full window.

## Corpus caveats, stated so the numbers are not read as more than they are

- **12 distinct meanings, 130 files.** Topics repeat across formats and languages, so this measures
  "did it find a document about the right topic", not discrimination among 130 distinct subjects.
- **The generated text is short, declarative sentences.** Real prose is messier.
- **The first run of this instrument scored Recall@1 of 0 % in every language**, because the corpus
  contained the generator script itself — a file holding every topic in all three languages, which
  ranked first for all 48 queries — and because the labels named one nominated file per topic while
  the same text sat in a dozen others. Both are fixed; the figure is recorded because it is what an
  uncorrected corpus of this shape produces, and nothing about the embedder changed between 0 % and
  90 %.
